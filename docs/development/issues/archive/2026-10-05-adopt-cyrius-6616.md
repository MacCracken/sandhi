## 1. The SIGPIPE comment's premise is stale (CYRIUS-2026-0025, net-1)

From cyrius 6.6.16 every `lib/net.cyr` socket write (`sock_send`, `sock_send_all`, `sock_send_a`) and the
async writers never raise SIGPIPE on a socket: Linux issues `sendto(fd, buf, n, MSG_NOSIGNAL, NULL, 0)`, macOS
sets `SO_NOSIGPIPE` per write (so sandhi's raw-`sys_socket` IPv6 paths are covered too). `write(2)` remains
only for an fd that is not a socket.

- `src/server/mod.cyr:1260` ("`net.cyr`'s `sock_send` is a bare `write(2)` with no `MSG_NOSIGNAL`, so a write
  to a peer that has closed the connection raises SIGPIPE …") and `:1469` ("sock_send is MSG_NOSIGNAL-less")
  should state the current premise: on cyrius ≥ 6.6.16 a socket write cannot raise SIGPIPE;
  `_sandhi_server_ignore_sigpipe` stays harmless and still covers a write to a pipe, so it may stay.
- (1.10.6 already moved the guard onto the stdlib's `signal_ignore`, so no code change is suggested.)
- sandhi's client paths, which all go through `sock_send`, are protected by the cyrius change with no sandhi edit.

## 2. `_sandhi_server_conn_blocking` is redundant (net-2, N4)

From 6.6.16 `sock_accept` returns a BLOCKING socket on every target whatever the listener's mode: on macOS it
clears the `O_NONBLOCK` a BSD `accept(2)` copies from the listener; on Windows it resets the inherited
`FIONBIO`. A failed reset closes the accepted socket and returns `Err(errno)` from `sock_accept` itself.

- `src/server/mod.cyr:1198` / `:1211`: against a cyrius ≥ 6.6.16 pin the helper always finds `O_NONBLOCK`
  clear and returns 0 — harmless, one extra `F_GETFL` per accept. sandhi may drop it (and its
  `tests/sandhi.tcyr:1576` row, or keep that row as a contract check on the accepted fd) once its minimum pin
  is 6.6.16.
- If it does: a failed reset now surfaces as `sock_accept`'s `Err(errno)` (fcntl's errno) rather than
  `Err(_SANDHI_ERRNO_ECONNABORTED)`; the accept-error policy should classify it as before.
- sandhi's Windows server path never had the workaround; on cyrius < 6.6.16 a non-blocking listener there
  handed native TLS a non-blocking fd. 6.6.16 fixes that with no sandhi change.

## 3. `sandhi_session_cache_supported()` now reads 1 on OpenSSL 3 under the libssl backend (tls-3, N6)

`tls_supports_session_resumption()` used to dlsym `SSL_CTX_set_session_cache_mode` — a macro in every OpenSSL,
so it read 0 on every OpenSSL 3, and so did `sandhi_session_cache_supported()`
(`src/tls_policy/session_cache.cyr:166`). From 6.6.16 the probe checks `SSL_CTX_ctrl`: **1 when the libssl
backend is active and libssl is loaded**, and `tls_ctx_set_session_cache_mode` really sets the mode (it was a
silent no-op returning 0).

- Under the **native** backend (the default) the probe stays 0, even if libssl was loaded in-process; the
  session/early-data verbs return their "unsupported" answer (0 / -1 / NOT_SENT) without touching libssl.
  (Before 6.6.16, once libssl was loaded, they handed the native ctx to libssl, which wrote into native memory.)
  `tls_supports_early_data()` can still read 1 under native once libssl is loaded; the 0-RTT verbs refuse
  there, so do not read it as "0-RTT works on this connection".
- A failed `tls_connect_complete` / `tls_accept_complete` on libssl is now final (`tls_read` returns the
  recorded `TLS_ERR_*`, `tls_write` `TLS_ERR_PROTOCOL`, a second complete 0). sandhi already `tls_close`s on 0,
  so nothing changes.
- **Worth adding:** with `sandhi_session_cache_enable(1)` on the libssl backend over OpenSSL 3, the cache now
  actually captures and installs — paths that have never run against OpenSSL 3. An end-to-end resumption test
  in sandhi's CI on the libssl backend: the second connect to the same host resumes, and each captured
  session is freed exactly once via `tls_session_free`. `tests/alloc.tcyr:1523` accepts 0 or 1 and needs no
  change.

## 4. `_sandhi_server_pool_inline` can key on `CHAN_BLOCKING` (thr-1)

Answers [`2026-10-04-cyrius-macos-chan-serial-under-real-threads.md`](2026-10-04-cyrius-macos-chan-serial-under-real-threads.md).
From 6.6.16 every thread peer exports `CHAN_BLOCKING` (1 on Linux, arm64 macOS, Windows; 0 on x86 macOS,
agnos, cx), and arm64 macOS and Windows have the Linux blocking-channel contract. The var does not exist
before 6.6.16, so this needs the pin. In `src/server/mod.cyr:2158` replace the target test

```
fn _sandhi_server_pool_inline(): i64 {
    #ifdef CYRIUS_TARGET_LINUX
    if (THREADS_CONCURRENT == 1) { return 0; }
    #endif
    return 1;
}
```

with the capability:

```
fn _sandhi_server_pool_inline(): i64 {
    if (CHAN_BLOCKING == 1) { return 0; }
    return 1;
}
```

- `CHAN_BLOCKING == 1` already implies real threads wherever it is 1, so the `THREADS_CONCURRENT` test adds
  nothing (and read 0 on Windows over real threads before 6.6.16).
- macOS (arm64) and Windows get a parallel pool; x86 macOS and agnos keep the inline path.
- The doc comment above the fn ("The stdlib exposes no channel capability, hence the target test") becomes
  history — point it at `CHAN_BLOCKING` and cyrius 6.6.16.
- Then re-run `test_server_request_budget_answers_408` (the 1.10.7 macOS row) with the pool path really
  taken on `macos-14`; it used to pass only through the inline path.
- No code change is needed for the Linux saturated-handoff deadlock 6.6.16 also fixed (see the resolution in
  the 2026-10-04 file) — only the pin.

## 5. The PEM-key-per-accept caveats can go (thr-2)

Answers [`2026-10-04-cyrius-tls-server-pem-key-decoded-per-accept.md`](2026-10-04-cyrius-tls-server-pem-key-decoded-per-accept.md):
from 6.6.16 the native stack decodes a PEM key once per process per distinct key text (measured: probe [8]
reads 0 B/request where it read 120).

- `docs/guides/server.md:226`, the `sandhi_server_options_tls` bullet. Replace "A **DER** key avoids a
  per-handshake decode: the stdlib decodes a PEM key on every accept and keeps ~120 B of it on the global heap
  each time (filed cyrius-side)." with "PEM or DER keys both serve at 0 B per request: since cyrius 6.6.16 the
  stdlib decodes a PEM key once per process (on cyrius ≤ 6.6.15 it decoded it on every accept and kept ~120 B
  of it on the global heap each time)."
- `programs/_server_tls_probe.cyr` check [8] (`:409-410`, header comment `:51-56`): the `per > 128` bound
  exists to tolerate the per-accept decode. On ≥ 6.6.16 the measurement is exactly 0, so require `per == 0`
  (or `m1 == m0`) and drop "the stdlib PEM key decode" from the message and comment — then a regression of the
  per-request arena or of cyrius's decode-once cache fails the gate instead of hiding under 128 B.
- Optional: a CHANGELOG note under the release that pins 6.6.16 that the PEM-key heap growth is gone, with
  no API change.

## Disposition — sandhi 1.10.9 (2026-10-08)

1. **SIGPIPE comments — taken.** `_sandhi_server_ignore_sigpipe`'s comment and `sandhi_server_run_opts`'s
   now state the 6.6.16 premise; the guard stays.
2. **`_sandhi_server_conn_blocking` — dropped.** `tests/sandhi.tcyr`'s
   `test_server_armed_accept_hands_out_blocking_fd` stays as the contract check on `sock_accept`, and gains a
   Windows arm (an empty read must wait out its timeout; Windows cannot read the mode back).
3. **libssl session cache on OpenSSL 3 — noted; the end-to-end resumption test is declined.** The paths it
   would exercise retire with the libssl backend at sandhi 2.0 (roadmap Batch A).
4. **`CHAN_BLOCKING` — taken.** New row `server/pool_parallel`. The request-budget row passes with the pool
   path on Linux, ecb, ach and cass (CI's `macos-14` job runs it too). Running the suite on cass also found
   that a stop-enabled blocking serve loop never left `accept` on Windows (Winsock ignores the listener's
   `SO_RCVTIMEO`, as XNU does); 1.10.9 polls the armed listener there as 1.10.4 did on macOS.
5. **PEM-key caveats — taken.** `docs/guides/server.md` and probe [8] (now `== 0`).

Both 2026-10-04 cyrius-side files move to `archive/` with this one.
